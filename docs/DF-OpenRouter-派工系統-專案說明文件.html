Part I

系統與技術設計

這個平台解決什麼問題、長什麼樣子、資料怎麼流、做了哪些工程決策與技術價值。

1專案摘要

把「員工各自拿金鑰亂打 API」變成「公司統一發放、統一代理、全程可稽核」的中控平台。

後端（FastAPI）作為所有 LLM 呼叫的 唯一代理出口，原生 API Key 加密存於後端、永不下發前端；使用者改持 SDK Key + User Token 雙因子憑證呼叫統一端點，由後端換發金鑰、限流、寫入稽核後回傳。

代代理層

單一後端出口，支援 OpenRouter（外網）與企業地端 OpenAI-compatible 模型，多金鑰 failover。

控中控管理

部門 → 專案 → 使用者 → 金鑰的階層式組織，模型白名單與用量成本三維度報表。

動自動開通

申請表單 + 規則路由 + AI 欄位驗證，信心足夠即全自動建立憑證並寄送通知信。

🧪 v2.0 → v2.1 新增能力 · AI 模型適配評審
平台不只代發，更能自我優化選型：背景 AI 評審針對每筆呼叫評估「原模型 vs 其他候選模型」的適配度並推薦更合適者（v2.0）；再對推薦模型真實重跑、以盲化「對比裁決」判定推薦輸出與原輸出孰優，給出建議維持 / 建議改用 / 平手與成本差，集中呈現於「AI 判決總覽」頁（v2.1）。

2目的

🔐 安全隔離

原生 API Key 集中後端加密保管，前端與使用者永遠取不到明文，杜絕金鑰外流與硬編碼風險。

💰 成本控管

每一次模型呼叫都歸戶到部門 / 專案 / 使用者，可逐層彙總 token 與美元成本，支援多應用分別計費。

📊 可稽核性

用量 Log 與操作稽核 Log 雙軌記錄，搭配 Seq 集中式 Log，異常可追蹤、責任可歸屬。

⚡ 統一接點

對使用者提供穩定、簡化的呼叫 schema；底層供應商、金鑰輪替、限流全部透明。

4核心概念與角色

理解平台前需先掌握的組織模型、憑證與權限角色。

組織模型

資源以階層方式組織，呼叫用量沿此階層逐層歸戶與彙總：

部門
成本中心，綁 OpenRouter Key 與 SDK Key
→
專案
部門下的應用，含專案代碼
→
使用者
員工，持 User Token
→
用量紀錄
每次呼叫歸戶到上述三層

三組呼叫憑證

X-SDK-Key

部門層級 · 存取金鑰

以部門為單位發放，代表「哪個部門的程式在呼叫」。DB 僅存 argon2id hash + 公開 prefix，明文僅建立時顯示一次。

X-User-Token

使用者層級 · 加密 payload

以員工為單位發放，AES-256-GCM 加密、內含使用者識別與發行時間，可由撤銷端點即時失效。

X-Project-Code

專案層級 · 歸戶代碼

決定這次呼叫的用量算到哪個專案；同把 SDK Key 可呼叫同部門任一專案。

認證 vs 歸戶
SDK Key + User Token 構成雙因子認證（兩者部門須一致，任一失敗一律回 401 unauthorized，不揭露是哪一項失敗）；Project Code 不屬認證祕密，而是用量歸戶欄位（缺漏或不屬該部門回 400）。

角色與權限

資源 / 動作管理員 admin一般使用者 user
部門 / 專案 / 金鑰 CRUD✅ 全平台❌
使用者管理 / 產生 · 撤銷 Token✅❌（僅可改自己密碼）
模型白名單與分級✅ 可開關 / 分級僅讀已啟用
用量與成本統計✅ 全部✅ 僅自身部門 / 個人
系統稽核 Log✅❌
API Key 申請表單✅ 檢視全部✅ 送出並檢視自己的

角色不固化於 JWT，每次請求即時由 DB 讀取，確保降級立即生效；前端僅依角色顯示 / 隱藏按鈕，實際過濾一律由後端完成。

5系統流程圖

流程 A：模型呼叫代理鏈（核心資料流）

使用者應用如何透過平台安全地呼叫 LLM。

🔑 安全關鍵
OpenRouter 原生 Key 全程僅存後端（AES-256-GCM），禁止出現在回應、Log、前端；使用者拿到的永遠是可撤銷的雙因子憑證。任一驗證失敗一律回 401 unauthorized，不揭露是哪一項失敗。

流程 B：API Key 申請自動開通（v1.9 系列核心創新）

把線下審核流程數位化、智慧化的混合式自動開通管線。

流程 C：AI 模型適配評審 + 真實重跑 + 對比裁決（v2.0–v2.1 背景管線）

以背景排程（taskiq + Redis）非同步評估「目前模型是否適配、有無更合適或更省的選擇」，並對推薦模型真實重跑後做盲化對比裁決，全程不影響使用者即時呼叫。

🔑 設計重點
全程背景非同步、不擋使用者即時呼叫；起始時間門檻（AI_EVAL_START_AT）讓舊資料不回溯分析以控成本；推薦與重跑一律排除 free 模型；裁決採盲化對比降低偏好偏差；兩道開關（AI_EVAL_ENABLED / AI_RERUN_ENABLED）可獨立關閉達零成本。

7版本演進

從 MVP 的 API 代理層，成長為「申請—審核—開通—通知」一條龍的自動化平台，再進化到 AI 模型適配評審與真實重跑對比裁決的自我選型能力。

v1.0 MVP
基礎多租戶框架：本地登入、部門 / 專案組織、OpenRouter 代理端點、SDK 雙因子認證、用量記錄與儀表板。
v1.1–1.2 · 模型管理 + 多 provider
白名單升級為 DB 驅動（分級 / 餘額同步）；支援地端 OpenAI-compatible 模型與 Key 級速率限制，端點收斂為 /model/chat。
v1.3–1.4 · SSO 與穩定化
整合 DF-SSO（OIDC 登入 + back-channel logout）；部署結構與 UX 穩定化修正。
v1.5–1.6 · 專案維度
「專案」（project_uid）串入代理鏈與稽核，儀表板三層篩選；管理動線整合（部門 → 專案 → 使用者 → 金鑰）。
v1.7–1.8 · 串流與檔案
新增 /model/chat/stream（SSE 打字機效果）；聊天請求支援 files（PDF 等，用量紀錄僅存檔名）。
v1.9–1.10 申請自動化
申請表單 + 生命週期 + 規則路由 + AI（Claude）欄位驗證自動開通 + 憑證通知信，線下審核完全數位化；申請欄位下拉化防呆。
v2.0.0 AI 模型評審地基
AI 評審資料表 + 判別模型設定 + 「AI 分析」頁；以 taskiq + Redis 導入背景任務基建。
v2.0.1–2.0.3 · 判別管線與展示
背景三評審打分管線（評估每筆呼叫的候選模型適配度）；DB 自我說明（table_catalog + COMMENT）；用量明細內嵌評審摘要。
v2.1.0 真實重跑 + 對比裁決
對 AI 推薦模型真實重跑，盲化對比裁決（建議維持 / 改用 / 平手）+ 成本差；「AI 判決總覽」頁並排真實輸出。
v2.1.1 · 成本可視化下放（2026-07-07）
Excel 匯出鏡射儀表板全維度（含專案 × 模型花費明細）；用量紀錄下放一般使用者查看自身部門，新增專案欄與篩選;修補無部門帳號的越權查詢。
v2.1.2 · 多輪對話直傳 + 帳號一鍵斷權（2026-07-14）
Chat API 開放 messages[] 多輪對話直傳（白名單透傳，與單輪互斥）與 temperature / max_tokens / response_format 三生成參數，明細頁分角色渲染；使用者停用即撤銷全部 Token（一鍵斷權，重新啟用需重發）。

8技術價值

這份專案展現的可遷移工程能力 —— 適合作為下一份工作的技術佐證。

🛡️ 安全工程

AES-256-GCM 對稱加密保管金鑰、argon2id 雜湊比對 SDK Key、雙因子憑證設計、錯誤訊息不洩漏細節（統一 401）、敏感資訊全程環境變數注入。

🏗️ 代理 / 閘道架構

後端作為唯一出口收斂所有對外呼叫，client 與 service 層職責分離；以 provider 抽象同時支援雲端與地端模型，新增供應商不動業務邏輯。

⚙️ 可靠性設計

多金鑰 failover、指數退避重試、依 Retry-After 處理 429、主動限速（RPM + 最小間隔）、地端排隊與逾時控制 —— 完整的韌性策略。

🌊 串流與非同步

SSE 串流端點、commit point 後禁止重試、斷線即取消上游避免額外計費、用量於 finally 確保入帳；BackgroundTask 解耦記帳與回應延遲。

🤖 AI 賦能自動化

以 LLM（Claude）做欄位語意驗證並輸出信心分數，結合規則路由形成 「規則 + AI」混合決策，把人工審核轉為條件式全自動開通。

📈 可觀測與稽核

用量 Log 與操作稽核 Log 雙軌、Seq 集中式 Log、成本可逐層歸戶，兼顧營運成本控管與資安追蹤需求。

🧱 工程化實踐

Monorepo 前後端分離、分層架構（api / service / repository / model）、Pydantic 契約、Alembic Migration、Swagger 文件、Docker Compose 部署與 healthcheck。

🤖 AI 自我選型 / 評審

以背景 taskiq + Redis 跑多評審打分、推薦模型真實重跑與盲化對比裁決，形成「生成 → 評審 → 重跑 → 裁決」閉環，把模型選型從人工經驗轉為資料驅動。

🔄 持續迭代能力

跨 v1.0 → v2.1 穩定演進，每版皆有設計提案（propose）與任務拆解（tasks）文件，向後相容（deprecated alias）、軟刪除保留歷史，展現規格驅動開發紀律。

💡 一句話總結
本專案完整涵蓋「安全 × 成本 × 可靠性 × 自動化」四大企業級平台關注點，從 0 到 1 設計並迭代一套對接多家 LLM 供應商的中控系統，是後端架構、API 閘道設計與 AI 整合能力的綜合展現。

10第一次登入管理後台

管理者（role=admin）才需要登入後台；一般使用者只拿三因子憑證、不進後台。

  1. 用瀏覽器開啟管理後台網址（見 §9 上表）。
  2. 以帳號 + 密碼登入。首位管理員的帳密由 Coolify 後台的環境變數 seed —— 帳號見 INITIAL_ADMIN_ACCOUNT、密碼見 INITIAL_ADMIN_PASSWORD（對應環境的 stack 設定內查看）。
  3. 登入後看到部門 / 用量 Dashboard，代表你已是管理員；後續可在「使用者管理」自行新增其他 admin。
  4. 若顯示無權限 / 被導回登入頁，表示帳密錯誤或該帳號 role 不是 admin —— 請確認 Coolify 環境變數值，或由現任管理員到「使用者管理」把你調為 admin。
登入方式
管理後台以帳號 + 密碼登入（帳密在 Coolify 環境變數）。若該 admin 另填了 INITIAL_ADMIN_EMAIL / 在使用者管理綁定 Email，亦可改用 DF-SSO（以 Email 對應本地帳號）登入。角色不固化於 JWT、每次請求即時由 DB 讀取，升降級立即生效；一般 user 不得進後台。

11後台分頁導覽

管理者會用到的主要分頁與用途。設定動線：部門 → OpenRouter Key → SDK Key → 專案 → 使用者。

分頁用途
部門管理建立部門（成本中心）；綁定 OpenRouter Key（加密保管、可多把 failover）；展開列管理該部門 SDK Key。
專案管理在部門下建立專案，取得對外呼叫要填的 專案代碼（Project Code）。
存取金鑰 / SDK Keys建立部門層級 SDK Key；明文 只在建立時顯示一次，DB 僅存 argon2id hash。
使用者管理建立成員、設定 role、針對 user 產生 / 撤銷 User Token。
模型白名單啟用 / 停用 / 分級模型、與 OpenRouter 同步清單、同步餘額；未啟用模型一律 403。
用量紀錄 / 統計依部門 / 專案 / 使用者三層查 token 與美元成本、延遲、成功與否。
申請表單檢視 API Key 線上申請與 5 態生命週期；信心不足者在此人工審核。
AI 分析v2.0+設定判別（裁決）模型；「AI 判決總覽」依用量紀錄分組檢視原模型 vs AI 推薦模型的真實輸出、對比裁決、成本差與延遲，可依編號排序 / 搜尋。

12維運核心觀念

操作前先記住這幾條，能避開九成「為什麼打不通 / 看不到明文」的疑惑。

  1. OpenRouter 原生 Key 只存後端（AES-256-GCM 加密），後台僅顯示遮罩；前端與使用者永遠拿不到明文。
  2. 兩套認證完全分離：管理後台用登入 Cookie；使用者呼叫用SDK Key + User Token + Project Code 三因子，互不相通。
  3. SDK Key / User Token 明文只顯示一次，遺失只能重發（舊的隨即撤銷，不可救回）。
  4. 白名單 DB 驅動（models.is_active）：未啟用就 403，與 OpenRouter 本身是否支援無關。
  5. 三因子須同部門：SDK Key、User Token 綁部門，Project 屬部門；任一不符回 401 或 400 project_invalid。
  6. 多為軟刪除：停用 / 刪除保留歷史用量，可追溯；角色變更即時生效。

13常見需求 Playbook

照情境找對應流程，依步驟點即可。

A · 新部門要上線：從 OpenRouter 申請 Key 到接入系統

情境：某部門 / 應用第一次要用平台呼叫 LLM，需先有一把 OpenRouter Key，再在後台建立整條歸戶鏈。
  1. 到 OpenRouter 申請 API Key：開 openrouter.ai 註冊 / 登入公司帳號 → 右上頭像 → Keys → Create Key（建議設定額度上限）→ 複製產生的 sk-or-…（只顯示一次）。OpenRouter 帳號由 IT 部門統一管理與儲值，各部門 Key 從該帳號產生。
  2. 後台「部門管理」新增部門（作為成本中心）。
  3. 在該部門貼入剛複製的 OpenRouter Key；系統會 AES-256-GCM 加密保管，同部門可放多把做 failover。
  4. 建立部門 SDK Key，記下明文（只顯示一次）。
  5. 「專案管理」在部門下建立專案，複製專案代碼。
  6. 「使用者管理」建立成員並產生 User Token，記下明文。
  7. 「模型白名單」確認要用的模型已啟用（必要時先與 OpenRouter 同步清單）。
  8. 把 SDK Key + User Token + 專案代碼 連同對應 API Base URL 交付使用者，請對方參考 §14 使用者：SDK 呼叫手冊。
💡 自動化捷徑
若改走線上「申請表單」，上面第 2–6 步可由規則路由 + AI 欄位驗證自動完成並寄送憑證信（見 §5 流程 B）；本 Playbook 是純手動 / 新部門首次接入的作法。

B · 幫某成員開通 / 撤銷呼叫權限

情境：部門已上線，只是要多開（或收回）一個人的呼叫資格。
  • 開通：「使用者管理」建立 user → 產生 User Token → 交付。部門既有的 SDK Key 與專案代碼沿用即可。
  • 撤銷：對該 user 撤銷 User Token（其所有舊 token 立即失效）；若要整個部門停擺，則撤銷該部門 SDK Key。

C · 憑證疑似外洩

情境：SDK Key 或 User Token 可能被貼到公開 repo / 外流。
  1. 立即撤銷：個人 → 撤銷該 User Token；整個部門 → 撤銷 / 重發 SDK Key。
  2. 重新產生新憑證並安全交付（受控後端 / CI Secret，勿走明文通訊）。
  3. 到「用量紀錄」檢視外洩期間是否有異常呼叫與成本。

D · 調整模型白名單

情境：要開放新模型、停用昂貴模型，或使用者回報某模型 403。
  • 啟用 / 停用：「模型白名單」切換 is_active；停用後使用者呼叫即回 403 model_forbidden。
  • 新模型：先與 OpenRouter 同步清單，再啟用。
  • 使用者自助查：請對方 GET /api/v1/allowed/models（免憑證）確認目前已啟用清單與 model_key。

E · 查某部門 / 專案花了多少

情境：要做成本分攤或抓異常用量。
  • 到「用量紀錄 / 統計」，依部門 / 專案 / 使用者三層篩選，彙總 token 與美元成本；web search 等 OpenRouter 額外計費也一併反映。

F · 線上申請單怎麼處理

情境：有人從前端送出 API Key 申請表單。
  • 多數自動：規則路由 + AI（Claude）驗證信心達標即自動建立憑證並寄送通知信（狀態 agent_done → done）。
  • 需人工：資料異常者取消（cancelled）；信心不足者落到 manual_pending，由 admin 在「申請表單」頁審核後，比照 Playbook A 後半 / B 手動開通。

G · 看 AI 是否建議換更合適的模型 v2.1

情境：想知道某些呼叫用更省 / 更好的模型是否更划算，作為調整白名單或預設模型的依據。
  1. 後台進「AI 分析 → AI 判決總覽」；先在「判別模型設定」確認已指定一個裁決模型（否則不會產生裁決）。
  2. 頁頂統計列看整體分布（建議維持 / 建議改用 / 平手 / 未裁決 / 失敗）；清單依用量紀錄編號分組，可用上方編號搜尋 / 排序定位特定一筆。
  3. 展開任一組看該筆「原模型 → AI 推薦模型」的對比裁決、信心、成本差與延遲；點[查看]開對照視窗，並排原模型與推薦模型的真實輸出原文與裁決理由。
  4. 若大量呈現「建議改用」且成本更省，可評估把該推薦模型納入白名單 / 設為預設；本頁僅供分析，不會自動改動任何設定。
運作方式
評審與重跑都在背景（taskiq + Redis）非同步執行，不影響使用者即時呼叫；裁決採盲化對比（裁決模型不知哪邊是原模型）以降低偏好偏差。需開啟對應環境開關 AI_RERUN_ENABLED / AI_RERUN_DISCRIMINATOR_ENABLED 才會產生重跑與裁決。

14使用者：SDK 呼叫手冊

SDK 使用者拿到三組憑證後，如何呼叫代理端點。完整使用者說明另見 docs/tutorial/openrouter-platform-user-guide.html。

① 端點與認證 Header

所有模型呼叫皆透過單一端點，三個 Header 皆必填：

HTTP
POST /api/v1/model/chat
Content-Type: application/json
X-SDK-Key: <SDK Key 明文>
X-User-Token: <User Token 明文>
X-Project-Code: <專案代碼>

平台提供測試與正式兩套環境，Base URL 不同；串流呼叫改用 /api/v1/model/chat/stream（SSE）。

② Request Body 欄位

欄位型別必填說明
modelstring是模型 id（例 google/gemini-2.5-flash），須在白名單內
textstring否使用者輸入文字
imagesstring[]否圖片 URL 或 data:image/...;base64,...
filesobject[]否PDF 等檔案；僅檔名寫入用量紀錄，內容不留存（法務考量）
toolsobject[]否原樣轉發；目前僅支援 OpenRouter server 端工具（如 web search）；兩種內容模式皆可搭配
messagesobject[]否多輪對話模式（v2.1.2）：OpenAI 風格 {role, content} 陣列（role 限 system/user/assistant；content 為字串或 text/image_url/file parts）。與 text/images/files 擇一，同時帶回 400；則數不設上限（模型 context window 為自然上限）
temperaturenumber否取樣隨機性 0–2（v2.1.2）；未帶走模型預設
max_tokensinteger否回覆長度上限 ≥1（v2.1.2）；未帶走模型預設
response_formatobject否結構化輸出（v2.1.2）：{"type":"json_object"} 或 {"type":"json_schema","json_schema":{...}}；其餘生成參數（top_p / stop 等）不開放

③ Response 統一格式

JSON · 成功
{
  "success": true,
  "code": 200,
  "data": "模型回答的文字內容...",
  "detail": "success"
}
JSON · 失敗
{
  "success": false,
  "code": 403,
  "data": null,
  "detail": "model_forbidden"
}

成功時 data 為模型回答的純文字字串（已剝除 id / usage / provider 等內部欄位）；detail 失敗時為錯誤碼。

④ 查詢可用模型清單（免憑證）

HTTP
GET /api/v1/allowed/models

回應 data[] 每筆的 model_key 即為 model 欄位要填入的值；僅回傳已啟用（白名單內）模型，定價等內部欄位不對外。

⚠ 憑證保管
SDK Key 與 User Token 只在建立時顯示一次，遺失只能請管理員重新發放（舊憑證隨即撤銷）。禁止寫死於前端 / 公開 repo / 客戶端 App，僅可存放於受控後端或 CI Secret。

16故障排除 Runbook

使用者回報「打不通」時，依症狀對照可能原因與第一步該檢查什麼。

症狀可能原因先檢查什麼
呼叫回 401 unauthorizedSDK Key / User Token 無效、已撤銷，或兩者不屬同一部門三因子是否同部門、是否被撤銷；必要時重發
呼叫回 400 project_invalid / project_code_required未帶 X-Project-Code，或專案不屬該部門 / 已停用「專案管理」確認代碼正確且專案啟用中
呼叫回 403 model_forbidden模型未在白名單，或已被停用「模型白名單」確認 is_active；或請使用者 GET /allowed/models
呼叫回 429 rate_limited短時間呼叫過於頻繁請使用者指數退避重試；必要時部門加第二把 OpenRouter Key
呼叫回 502 openrouter_unavailableOpenRouter 服務異常，或部門未正確綁定有效 Key「部門管理」確認 OpenRouter Key 有效、餘額足夠
整個部門都打不通部門 OpenRouter Key 失效 / 額度用盡，或 SDK Key 被撤部門頁檢查 Key 狀態與餘額同步結果
串流（SSE）沒有逐字輸出中間 proxy 緩衝，或對 internal 模型用了串流端點串流僅支援 OpenRouter 模型；curl 加 -N 關閉緩衝
完整錯誤碼對照
每個 detail 錯誤碼的逐項說明與處理建議，見 §14 使用者：SDK 呼叫手冊 與 docs/tutorial/openrouter-platform-user-guide.html 的「錯誤碼對照」。
